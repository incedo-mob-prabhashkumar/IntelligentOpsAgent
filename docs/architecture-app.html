AI IT Support Assistant

A stateful support assistant for employee help requests, ticket actions, knowledge lookup, and system-status checks. It combines a Streamlit UI, a decision-driven LangGraph workflow, and grounded data access using PostgreSQL-backed tools and semantic retrieval.

Core responsibilities

  • Understand user intent from natural language.
  • Route requests to the correct local tool or validation branch.
  • Maintain state across multiple turns in a conversation.
  • Validate fields before ticket creation and update operations.
  • Return grounded user-friendly answers with structured output.

Primary data domains

  • employees
  • knowledge_base
  • tickets
  • system_status

Typical user journeys

  • Check if the VPN is down.
  • Find the status of a support ticket.
  • Ask for help with employee access issues.
  • Open a new ticket after validation.
  • Update an existing ticket summary.

Technical component map

1. UI / interaction layer

  • app.py initializes the Streamlit session state and renders chat + tool results.
  • Conversation history is stored in session memory and persisted across turns.
  • It also exposes trace-level routing and structured data output for debugging.

2. Business service layer

  • src/service.py wraps the LangGraph workflow and manages the active request context.
  • ITSupportAgent.handle_message() is the main entry point for user requests.
  • It normalizes inputs and returns both text and structured trace results.

3. Orchestration layer

  • src/agent_graph.py defines the graph nodes and conditional transitions.
  • The graph detects intent, handles pending confirmation state, and validates writes.
  • It is responsible for routing to knowledge, employee, ticket, or status tools.

4. Retrieval and AI layer

  • src/llm_router.py performs intent classification and response generation.
  • src/tools.py executes queries and writes against the business data model.
  • Sentence embeddings support semantic matching while regex and rule-based logic serve as a fallback.

5. Data persistence layer

  • src/models.py defines the SQLAlchemy ORM model schema.
  • src/database.py handles schema initialization and application startup setup.
  • src/config.py loads provider settings from environment variables.

6. State and workflow state

  • src/state.py captures user input, intent, pending fields, and tool output.
  • State carries context across multi-turn confirmation and ticket-creation flows.
  • It is critical for safe continuation when the user supplies follow-up information.

Request execution pipeline

1. Receive inputUser message enters the chat completion loop. Session context from the previous turn is available.
2. Normalize stateThe current graph state is updated with user input, pending fields, and prior local memory.
3. Route intentDeterministic checks run first, then the semantic classifier is used to choose the best intent.
4. Validate safetyWrite paths require employee validation, ticket existence, duplication checks, and required field checks.
5. Execute toolAppropriate tool reads or updates the business database and returns structured payloads.
6. Return resultResponse generation combines the tool output with user-friendly language and renders the table.

Decision flow pseudocode

def handle_message(user_message, context):
    state = merge_context(context, user_message)
    route = detect_intent(state)

    if route == "ticket_creation":
        if not employee_id_present(state):
            return ask_for_employee_id()
        if duplicate_ticket_exists(state):
            return reject_duplicate_ticket()
        if not required_fields_present(state):
            return ask_for_missing_fields()
        return create_ticket(state)

    if route == "ticket_update":
        if not ticket_id_present(state):
            return ask_for_ticket_id()
        return update_ticket(state)

    if route == "knowledge_search":
        return search_knowledge(state)

    if route == "system_status":
        return get_system_status(state)

    return generate_small_talk_response(state)

Business scenarios covered

Knowledge

VPN password reset

Query is routed to the knowledge tool and matched semantically with article embeddings + lexical fallback to resolve paraphrased descriptions.

Employee

Employee lookup

Employee ID or partial profile text triggers a lookup against the employees table. Data is returned in a normalized row structure.

Ticket lookup

Status check

Natural language query uses context to resolve employee_id or ticket_id and return matching ticket records with state details.

Ticket create

New issue creation

Creates a new ticket only after employee validation, duplicate detection, and field-completeness checks pass.

Duplicate prevention

Repeated symptoms

Open tickets are compared by similarity to prevent duplicate creation and maintain clean ticket hygiene.

System status

Infrastructure health

Status lookup reads the system_status table and returns current service state, timestamps, and service-level notes.

Representative request patterns

1. “My VPN is not working. Please raise a ticket.” → stateful ticket creation flow with employee validation and issue summary capture.
2. “What is the status of my laptop issue? EMP1024” → employee context resolves the related ticket set for lookup.
3. “I need help resetting my VPN password” → semantic match against knowledge_base with lexical fallback.
4. “Update TKT1001 summary…” → existing ticket validation before update, followed by write confirmation.
5. “Check the system health” → direct retrieval from system_status and summary presentation.

Safety and validation

  • All write operations run through validation guardrails.
  • Employee existence and ticket existence must be confirmed before mutation.
  • Duplicate ticket logic reduces repeated support requests and noisy state.
  • Response text is grounded in actual tool output, preventing fabricated ticket facts.

Failure handling

  • Database startup failures surface warnings without crashing the chat session.
  • Semantic retrieval failures degrade to lexical matching rather than total failure.
  • LLM generation issues fall back to deterministic response handling.
  • Ambiguous confirmation-state prompts request clarification instead of mutating records.

Operational quality

  • Coverage includes routing, schema validation, and critical business scenarios.
  • The architecture is designed to support future RBAC and migration patterns.
  • It is extensible for ticket lifecycle operations such as close, reopen, assign, and escalate.

Why SentenceTransformer is primary

Semantic intent matching
Natural-language requests are not usually expressed as exact tokens. SentenceTransformers map text to a shared embedding space and can measure similarity between paraphrased user queries and stored knowledge entries or expected intent clusters.
Problem-specific relevance
Queries like “remote access keeps dropping” and “VPN disconnect” are semantically equivalent in an IT support context even when they do not share the same keywords. Semantic matching improves relevance without hardcoding every phrase.
Grounded ranking
In this architecture, semantic retrieval is used to rank the most relevant knowledge items before returning them. This improves recall while retaining an explicit fallback chain.

Why heuristic search is secondary

Determinism
Heuristic logic is explicit and deterministic. It is well suited for exact identifiers, required fields, and confirmation states where predictable branch selection is critical.
Safety checks
High-risk operations such as ticket creation or update must not rely solely on a high-level similarity score. The heuristic layer ensures the application can validate known IDs and required data with predictable outcomes.
Fallback reliability
If semantic scoring is weak, absent, or unavailable, the rule-based layer ensures the assistant still handles known patterns correctly rather than failing silently.
Practical design decision: SentenceTransformer is the primary understanding layer because it handles semantic variation, while heuristics remain the authoritative fallback for exact-data tasks and safety-sensitive actions.

Design principles

The system prioritizes grounded data access, validated writes, and stateful conversation continuity so that the assistant behaves as a reliable internal operations tool rather than a general-purpose chatbot.
